## 1. RAG end to end: ingestion, chunking, embedding, indexing, retrieval, reranking, generation, advanced variants, failure modes, long-context vs RAG

### Takeaway
In 2026, production RAG is a multi-stage pipeline:
- parse, then chunk, with contextual enrichment added
- embed (dense) plus build a BM25 (sparse) index
- hybrid retrieve, fused with RRF
- rerank with a cross-encoder, typically 150 candidates down to 20
- generate grounded answers with citations

Anthropic's Contextual Retrieval benchmark is still the most-cited evidence. Contextual embeddings plus contextual BM25 plus reranking cut retrieval failures by 67%. For corpora under about 200K tokens, put everything in a cached long-context prompt instead of building RAG.

### Cited Findings

**Foundations**
- **[OLDER]** RAG was introduced by Lewis et al. (2020). It combines a parametric seq2seq generator with a non-parametric dense vector index of Wikipedia accessed by a neural retriever, trained end-to-end — [arXiv 2005.11401 (bg)](https://arxiv.org/abs/2005.11401)

**Contextual Retrieval (Anthropic, Sept 19, 2024) [OLDER but still the reference benchmark]** — [Anthropic (fetched)](https://www.anthropic.com/engineering/contextual-retrieval)
- **Method:** each chunk gets a 50–100 token chunk-specific context prepended before embedding and before BM25 indexing. The context is generated by Claude 3 Haiku from a prompt containing the whole document plus the chunk.
- **Cost:** with prompt caching the document stays loaded, so the one-time cost is about $1.02 per million document tokens. The example assumes 800-token chunks, 8K-token documents, 50-token instructions and 100 tokens of context per chunk.
- **Results** (failure rate in the top-20 chunks, baseline 5.7%):

| Configuration | Failure reduction | Failure rate |
|---|---|---|
| Contextual embeddings | −35% | 3.7% |
| + contextual BM25 | −49% | 2.9% |
| + reranking | −67% | 1.9% |

- **Top-k:** pass the top 20 chunks, which beat 10 and 5. For reranking, retrieve the top 150, rerank, and keep 20. Too much context can distract the model, so tune k per use case.
- **Long context vs RAG:** if the knowledge base is under 200,000 tokens (about 500 pages), include it all in the prompt and skip RAG. Prompt caching can cut latency by more than 2x and cost by up to 90%.

**Chunking strategies**
- **Fixed-size / recursive:** split on token count, or recursively on separators (paragraph, then sentence, then word) with overlap. This is the default in most frameworks. OpenAI file search defaults to 800-token chunks with 400-token overlap — [OpenAI file search docs (bg)](https://platform.openai.com/docs/assistants/tools/file-search)
- **Semantic chunking:** split where embedding similarity between adjacent sentences drops. Bedrock Knowledge Bases offers fixed-size, hierarchical (parent/child), semantic, no chunking, and custom chunking via Lambda — [AWS Bedrock KB docs (bg)](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking.html)
- **Late chunking [OLDER, 2024]** (Günther et al., Jina AI):
  - It embeds the whole document with a long-context embedding model first, then mean-pools token embeddings per chunk span. Each chunk vector therefore carries document-wide context.
  - It needs no extra training. It is an alternative to LLM-generated contextual prefixes.
  - [arXiv 2409.04701 (bg)](https://arxiv.org/abs/2409.04701)

**Embedding and indexing**
- **Matryoshka representation learning:** lets embedding vectors be truncated to fewer dimensions with graceful quality loss, trading storage and latency against recall. OpenAI's text-embedding-3 models expose a `dimensions` parameter built on this — [arXiv 2205.13147 (bg)](https://arxiv.org/abs/2205.13147)
- **Late-interaction retrieval (ColBERT):** keeps per-token embeddings and scores with MaxSim. It sits between bi-encoders (fast, precompute docs) and cross-encoders (accurate, slow) — [arXiv 2004.12832 (bg)](https://arxiv.org/abs/2004.12832)

**Retrieval**
- **Hybrid search fusion:** usually done with Reciprocal Rank Fusion, score(d) = Σ 1/(k + rank_i(d)) with k = 60 — [Cormack et al., SIGIR 2009 (bg)](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf)
- **HyDE [OLDER, Dec 2022]:** an instruction-following LLM writes a hypothetical answer document. That document is embedded (the paper uses the unsupervised Contriever encoder), and the vector retrieves real documents. It enables zero-shot dense retrieval without relevance labels — [arXiv 2212.10496 (bg)](https://arxiv.org/abs/2212.10496)
- **Multi-query / query decomposition:** an LLM rewrites a query into several sub-queries, retrieves for each, and fuses the results (often with RRF). Bedrock KB exposes "query decomposition" as a retrieval option — [AWS Bedrock KB docs (bg)](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-config.html)

**Reranking**
- Cross-encoder rerankers score (query, chunk) pairs jointly. In the Contextual Retrieval study, adding a reranker took failure reduction from 49% to 67% — [Anthropic (fetched)](https://www.anthropic.com/engineering/contextual-retrieval)
- Cohere Rerank 3.5 and Amazon Rerank 1.0 are available as managed rerankers through the Bedrock Rerank API and Knowledge Bases — [AWS Bedrock rerank docs (bg)](https://docs.aws.amazon.com/bedrock/latest/userguide/rerank.html)

**Generation with citations**
- Anthropic's Citations API (Jan 2025) returns `cited_text` spans tied to supplied documents. It chunks documents into sentences automatically, and cited text does not count toward output tokens — [Anthropic Citations docs (bg)](https://docs.claude.com/en/docs/build-with-claude/citations)
- Anthropic's multi-agent research system uses a dedicated CitationAgent that post-processes documents and the report to attach citations to claims — [Anthropic (fetched)](https://www.anthropic.com/engineering/multi-agent-research-system)

**Advanced variants**
- **GraphRAG [OLDER, Apr 2024]** (Microsoft Research, Edge et al.):
  - An LLM extracts an entity/relationship graph, Leiden community detection clusters it, and the LLM pre-summarizes each community.
  - Global "sensemaking" questions are answered map-reduce style over community summaries.
  - It beat naive vector RAG on comprehensiveness and diversity on corpora of about 1M tokens.
  - [arXiv 2404.16130 (bg)](https://arxiv.org/abs/2404.16130)
- **LazyGraphRAG (Microsoft Research, Nov 2024):** defers LLM summarization to query time. Indexing costs match vector RAG and are about 0.1% of full GraphRAG — [Microsoft Research blog (bg)](https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/)
- **Managed GraphRAG on AWS:** Bedrock Knowledge Bases supports GraphRAG backed by Amazon Neptune Analytics — [AWS docs (bg)](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-build-graphs.html)
- **Agentic RAG:** an LLM plans queries, chooses sources, runs parallel searches and iterates.
  - Azure's "agentic retrieval" (Foundry IQ) decomposes complex questions into subqueries, runs them in parallel across knowledge sources, semantically reranks, and returns cited results — [Microsoft Foundry blog (search snippet)](https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/-/4470812); [ITNext analysis](https://itnext.io/from-classic-rag-to-agentic-retrieval-inside-microsofts-foundry-iq-architecture-7338e1bd4eb4)
  - Research precursors are Self-RAG, where the model learns reflection tokens to decide when to retrieve and to critique outputs ([arXiv 2310.11511 (bg)](https://arxiv.org/abs/2310.11511)), and Corrective RAG, where a retrieval evaluator triggers web search or refinement when retrieved docs are poor ([arXiv 2401.15884 (bg)](https://arxiv.org/abs/2401.15884)).

**Failure modes**
- Barnett et al. (2024) list seven failure points — [arXiv 2401.05856 (bg)](https://arxiv.org/abs/2401.05856):
  1. missing content
  2. missed top-ranked documents
  3. not in context (lost at consolidation)
  4. not extracted
  5. wrong format
  6. incorrect specificity
  7. incomplete answers
- **"Lost in the middle" [OLDER, 2023]:** LLM accuracy is highest when relevant information sits at the start or end of a long context and degrades in the middle. This argues for reranking and limiting k — [arXiv 2307.03172 (bg)](https://arxiv.org/abs/2307.03172)
- **Lost context from chunking:** a chunk like "The company's revenue grew by 3%" lacks the company name and period once chunked. This is what Contextual Retrieval fixes — [Anthropic (fetched)](https://www.anthropic.com/engineering/contextual-retrieval)

### Inferences
- **Default 2026 recipe:**
  - parse with layout-aware parsers (tables and figures matter)
  - recursive or semantic chunks of about 300–800 tokens with overlap
  - contextual prefixes (generated cheaply with prompt caching) or late chunking
  - hybrid dense + BM25, fused with RRF, metadata and ACL filtering at query time
  - cross-encoder rerank of about 100–150 candidates to 10–20
  - citation-enforced generation
- **Long context vs RAG decision:** small, stable corpora (under about 200K tokens) favor a cached full-context prompt. Large, changing, permissioned or multi-tenant corpora still need RAG, because per-query cost grows linearly with context and caching only helps an identical prefix. Mid-context degradation also argues against stuffing.
- **GraphRAG:** worth its indexing cost mainly for global or thematic questions across a corpus. For pinpoint fact lookup, hybrid + rerank is usually enough.

- I found no 2026 head-to-head benchmark of late chunking vs contextual retrieval vs plain chunking.

## 3. Agents: the loop, tool calling, planning patterns, memory, human-in-the-loop; Anthropic's "Building effective agents" patterns

### Takeaway
An agent is an LLM running tools in a loop with feedback from the environment, plus memory and stopping conditions.

Anthropic's taxonomy (Dec 2024) is still the standard vocabulary:
- **Workflows**, which follow predefined code paths: chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer.
- **Agents**, which are LLM-directed.

Production lessons (2025–26) center on four things:
- context and token economics (multi-agent uses about 15x chat tokens)
- tool and agent-computer interface (ACI) design
- resumable state
- code execution as a way to cut tool-call token overhead

### Cited Findings

**Anthropic, "Building effective agents" (Dec 19, 2024) [OLDER, still canonical]** — [Anthropic (fetched)](https://www.anthropic.com/engineering/building-effective-agents)
- **Workflows vs agents:** workflows are LLMs and tools orchestrated through predefined code paths. Agents are LLMs that dynamically direct their own processes and tool use.
- **Building block:** the augmented LLM, meaning an LLM with retrieval, tools and memory that it uses actively (writing its own queries, choosing tools).

| Pattern | How it works | When to use |
|---|---|---|
| Prompt chaining | Each call processes the previous output, with programmatic "gates" between steps | Fixed subtasks; trades latency for accuracy |
| Routing | Classify the input, then dispatch to a specialized prompt or model | Distinct input categories; e.g., easy queries go to a small model |
| Parallelization: sectioning | Independent subtasks run concurrently | e.g., a guardrail model screening alongside the main response |
| Parallelization: voting | The same task runs N times | Diverse outputs for review or evaluation |
| Orchestrator-workers | A central LLM decomposes the task dynamically, delegates, and synthesizes | Subtasks can't be predicted, e.g., multi-file code changes |
| Evaluator-optimizer | A generator plus a critic loop | Clear evaluation criteria where iteration measurably helps |

- **Autonomous agents:** plan and act, check environmental "ground truth" (tool results, code execution) each step, pause for humans at checkpoints, and use stopping conditions such as max iterations. They cost more and compound errors, so test them extensively in sandboxes with guardrails.
- **Framework advice:** start with raw LLM APIs. Frameworks can obscure prompts and responses, so understand the underlying code and remove abstraction when moving to production.
- **Three principles:** simplicity, transparency (show planning steps), and careful ACI design.
- **Tool design:**
  - Write docs with examples, edge cases and clear boundaries.
  - Test many inputs.
  - "Poka-yoke" tools so they are hard to misuse; e.g., requiring absolute file paths eliminated errors.
  - Use formats close to natural text, and avoid formats that need manual line counting or string escaping.

**Planning patterns**
- **[OLDER, Oct 2022] ReAct:** interleaves reasoning traces ("Thought") with actions ("Act") and observations. It is the template for the modern tool-calling loop — [arXiv 2210.03629 (bg)](https://arxiv.org/abs/2210.03629)
- **Plan-and-execute / plan-and-solve:** first produce an explicit plan, then execute steps, optionally re-planning. Execution can use cheaper models — [Plan-and-Solve, arXiv 2305.04091 (bg)](https://arxiv.org/abs/2305.04091)
- **Reflexion:** agents store verbal self-reflections in an episodic memory to improve on later trials — [arXiv 2303.11366 (bg)](https://arxiv.org/abs/2303.11366)

**Orchestrator-worker multi-agent in production** (Anthropic Research feature, June 13, 2025) — [Anthropic (fetched)](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Architecture:** a lead agent (Opus 4) plans and spawns parallel subagents (Sonnet 4). A CitationAgent attaches sources.
- **Result:** it beat single-agent Opus 4 by 90.2% on an internal research eval.
- **Token economics:** agents use about 4x chat tokens; multi-agent systems about 15x. On BrowseComp, token usage alone explained 80% of performance variance, and three factors explained 95%.
- **Memory:** the lead agent saves its plan to external memory because context beyond 200K tokens gets truncated.
- **Reliability:** errors compound, so systems resume from checkpoints rather than restarting. They use full production tracing, and "rainbow deployments" keep old and new versions running during long agent runs.
- **Synchronous bottleneck:** the lead waits for each batch of subagents.
- **Poor fits for multi-agent:** tasks needing shared context or heavy inter-agent dependencies, most coding tasks, real-time coordination, and low-value tasks.

**Tool calling at scale / code execution**
- **Anthropic "Code execution with MCP" (Nov 4, 2025)** — [Anthropic (fetched)](https://www.anthropic.com/engineering/code-execution-with-mcp)
  - **Problem:** loading every tool definition and routing every intermediate result through the model wastes context.
  - **Approach:** present MCP servers as code APIs on a filesystem (e.g., `./servers/google-drive/getDocument.ts`). The agent loads only the definitions it needs and writes code that calls the tools in a sandbox.
  - **Savings:** a Drive-to-Salesforce example dropped from about 150,000 to 2,000 tokens (98.7%).
  - **Other benefits:** progressive disclosure, filtering data in code, privacy (e.g., PII tokenization), and saved "skills".
  - **Caveat:** it needs secure sandboxing, resource limits and monitoring.

**Memory**
- **Short-term memory:** the conversation or thread state, checkpointed. **Long-term memory:** persists across sessions. LangGraph supports both, plus "durable execution", where agents survive failures and resume — [LangGraph GitHub (fetched)](https://github.com/langchain-ai/langgraph)
- The OpenAI Agents SDK provides "Sessions" (automatic conversation history management) — [openai-agents-python (fetched)](https://github.com/openai/openai-agents-python)
- Bedrock AgentCore Memory is "managed memory infrastructure for personalized agent experiences" — [AgentCore samples (fetched)](https://github.com/awslabs/amazon-bedrock-agentcore-samples)
- **[OLDER, 2023] MemGPT:** OS-style virtual context management that pages information between the context window and external storage. It is the intellectual root of many long-term memory services — [arXiv 2310.08560 (bg)](https://arxiv.org/abs/2310.08560)

**Human-in-the-loop (HITL)**
- **LangGraph:** interrupts let users inspect and modify agent state mid-run — [LangGraph GitHub (fetched)](https://github.com/langchain-ai/langgraph)
- **Claude Agent SDK:** HITL and policy are enforced with `PreToolUse` hooks (returning `permissionDecision: "deny"`), `allowed_tools` / `disallowed_tools`, `permission_mode`, and a `can_use_tool` callback — [claude-agent-sdk-python (fetched)](https://github.com/anthropics/claude-agent-sdk-python)
- **Google ADK:** a "tool confirmation flow" for human approval — [adk-python (fetched)](https://github.com/google/adk-python)
- **OpenAI Agents SDK:** lists "Human in the loop" as a core primitive — [openai-agents-python (fetched)](https://github.com/openai/openai-agents-python)
- **MCP:** adds URL-mode elicitation (2025-11-25), so a server can send a user to a URL (e.g., an OAuth or payment page) — [MCP 2025-11-25 changelog (fetched)](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-11-25/changelog.mdx)

### Inferences
- **Default architecture:** a single agent with well-designed tools first. Add routing to cheap models for easy traffic. Move to orchestrator-workers only for broad, parallelizable, high-value tasks, because the 15x token multiplier dominates cost.
- **Treat context as a budget:** code-execution-over-MCP, progressive tool disclosure, external memory files and summarization are now standard ways to keep long-running agents inside context limits.
- **HITL is a runtime concern, not a prompt concern:** implement it as pre-tool hooks or permission callbacks plus durable pause/resume. Approvals can take hours, so a synchronous process can't wait on them.

## 4. Agent frameworks and runtimes

### Takeaway
By October 2026 the landscape has consolidated into two layers.

**Code-first SDKs:**
- Claude Agent SDK
- OpenAI Agents SDK
- LangGraph
- LlamaIndex
- CrewAI
- Microsoft Agent Framework (MAF 1.0 GA Apr 2026, replacing Semantic Kernel and AutoGen)
- Google ADK

**Managed hyperscaler agent runtimes:**
- Amazon Bedrock AgentCore (GA Oct 2025)
- Gemini Enterprise Agent Platform, formerly Vertex AI Agent Engine (rebranded Apr 2026)
- Microsoft Foundry Agent Service (hosted agents GA Jul 2026, per a secondary source)

Runtimes are framework-agnostic and converge on the same components: serverless isolated runtime, tool gateway (MCP), memory, identity, code interpreter, browser, observability via OpenTelemetry, policy and evals.

### Cited Findings

**Claude Agent SDK**
- It runs the Claude Code agent harness as a library (`pip install claude-agent-sdk`, Python 3.10+, CLI bundled).
- **APIs:** `query()` for one-shot async streaming, and `ClaudeSDKClient` for bidirectional sessions with custom tools and hooks.
- **Tools:** the built-in Claude Code toolset (Read/Write/Edit/Bash, etc.). Custom tools are written with `@tool` and bundled as **in-process SDK MCP servers** (`create_sdk_mcp_server`), which avoids subprocess and IPC overhead. These can be mixed with external stdio MCP servers.
- **Control:** hooks such as `PreToolUse`, and permissions (`allowed_tools`, `disallowed_tools`, `permission_mode`, `can_use_tool`).
- **Other features:** programmatic subagents, and sessions with resume and fork.
- [GitHub (fetched)](https://github.com/anthropics/claude-agent-sdk-python)
- It was renamed from "Claude Code SDK" to "Claude Agent SDK" in Sept 2025 — [Anthropic (bg)](https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk)

**OpenAI Agents SDK**
- **Primitives:** Agents, Sandbox agents (long tasks inside a container), Realtime and Voice agents, Agents-as-tools and Handoffs, Tools (functions, MCP, hosted tools), Guardrails (input/output validation), Human-in-the-loop, Sessions, and built-in Tracing.
- **Providers:** provider-agnostic. It supports the Responses and Chat Completions APIs plus "100+ other LLMs" via any-llm or LiteLLM.
- [GitHub (fetched)](https://github.com/openai/openai-agents-python)
- It launched March 2025 alongside the Responses API, succeeding the experimental Swarm — [OpenAI (bg)](https://openai.com/index/new-tools-for-building-agents/)
- **[LEGACY]** The OpenAI Assistants API shutdown was scheduled for **Aug 26, 2026**. The replacement is the Responses API plus the Conversations API, which reached feature parity. ## 5. Protocols: Model Context Protocol (MCP) and Agent2Agent (A2A)

### Takeaway
MCP, introduced by Anthropic in Nov 2024 and donated to the Linux Foundation's Agentic AI Foundation in Dec 2025, is the de facto agent-to-tool standard.

Its **2026-07-28 revision** is the big architectural change: MCP becomes **stateless**.
- The initialize handshake and `Mcp-Session-Id` are gone.
- Multi Round-Trip Requests replace server-initiated sampling and elicitation.
- Streamable HTTP requests carry routing headers.
- List results become cacheable.
- Sampling, Roots and Logging are deprecated.

A2A (Google, Apr 2025) is the agent-to-agent complement. It reached **v1.0 on Mar 12, 2026** under Linux Foundation governance.

### Cited Findings

**MCP basics (bg unless noted)**
- **Origin [OLDER]:** introduced by Anthropic on Nov 25, 2024 — [Anthropic (bg)](https://www.anthropic.com/news/model-context-protocol)
- **Architecture:**
  - A **host** (the LLM application) runs one **client** per server connection.
  - **Servers** expose capabilities over JSON-RPC 2.0.
  - Server primitives are **tools** (model-controlled actions), **resources** (application-controlled context data) and **prompts** (user-controlled templates).
  - Client primitives are sampling, roots and elicitation.
  - [MCP spec (bg)](https://modelcontextprotocol.io/specification/2025-11-25)
- **Transports:**
  - **stdio:** the client launches the server as a subprocess and exchanges newline-delimited JSON-RPC over stdin/stdout.
  - **Streamable HTTP:** a single HTTP endpoint taking POST and GET; the server may reply with JSON or an SSE stream. It was introduced in 2025-03-26, replacing the 2024-11-05 HTTP+SSE transport.
  - [MCP transports spec (bg)](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)
- **Authorization (HTTP transports):**
  - Based on OAuth 2.1.
  - Since 2025-06-18 the MCP server is an OAuth resource server, using Protected Resource Metadata (RFC 9728) and Resource Indicators (RFC 8707) to bind token audience. Token passthrough is forbidden.
  - stdio servers take credentials from the environment instead.
  - 2025-06-18 also added structured tool output and elicitation, and removed JSON-RPC batching.
  - [MCP authorization spec (bg)](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)

**Spec release history** — [GitHub releases (fetched)](https://github.com/modelcontextprotocol/modelcontextprotocol/releases)
- 2024-11-05 → 2025-03-26 → 2025-06-18 → 2025-11-25 (stable Nov 25, 2025) → 2026-07-28 (RC May 29, stable Jul 28, 2026). Version negotiation allows cross-version interop.

**2025-11-25 revision** — [changelog (fetched)](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-11-25/changelog.mdx)
- **Auth:** OpenID Connect Discovery for authorization servers; incremental scope consent via `WWW-Authenticate`; **Client ID Metadata Documents (CIMD)** recommended for client registration; PRM discovery aligned to RFC 9728 with a `.well-known` fallback.
- **Metadata:** icons on tools, resources and prompts; tool-naming guidance.
- **Elicitation and sampling:** URL-mode elicitation; standards-based enum schemas; sampling supports tool calling (`tools`, `toolChoice`).
- **Tasks:** **experimental Tasks**, meaning durable requests with polling and deferred results.
- **Transport fixes:** Streamable HTTP must return 403 for invalid Origin; input-validation errors are returned as tool execution errors so models self-correct.
- **Schemas:** JSON Schema 2020-12 is the default.
- **Governance:** formal governance structure, Working and Interest Groups, and an SDK tiering system.

**2026-07-28 revision (current)** — [MCP blog (fetched)](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- **Stateless:** retires `initialize`/`initialized` and `Mcp-Session-Id` (SEP-2575, SEP-2567). Every request carries its protocol version, client identity and capabilities in `_meta`.
  - An optional `server/discover` RPC advertises server capabilities.
  - Any request can hit any instance behind a plain round-robin load balancer with no shared storage.
  - Stateful servers should mint explicit handles via tools that the model passes back.
- **Multi Round-Trip Requests (SEP-2322):** replace server-initiated `elicitation/create`, `sampling/createMessage` and `roots/list`. The server returns `resultType: "input_required"`, and the client retries with `inputResponses`.
- **Header-based routing (SEP-2243):** Streamable HTTP requests must include `Mcp-Method` and `Mcp-Name` headers, so gateways, rate limiters and WAFs can route without parsing bodies.
- **Cacheable lists (SEP-2549):** `tools/list`, `prompts/list`, `resources/list` and `resources/read` return `ttlMs` and `cacheScope` in deterministic order. Stable ordering helps keep upstream prompt caches stable.
- **Auth hardening:**
  - RFC 9207 issuer validation (SEP-2468)
  - `application_type` in DCR, fixing localhost redirects for desktop and CLI apps (SEP-837)
  - issuer-bound credentials (SEP-2352)
  - **Dynamic Client Registration formally deprecated in favor of CIMD**
- **Extensions framework:** Tasks moved to the `io.modelcontextprotocol/tasks` extension (SEP-2663) with `tasks/get` and `tasks/update`. Notifications move to a single `subscriptions/listen` stream. MCP Apps and Enterprise Managed Authorization are also extensions.
- **Deprecations:** Roots, Sampling and Logging (SEP-2577), supported for at least 12 more months. The legacy HTTP+SSE transport has a year-long off-ramp. There is a formal 12-month minimum deprecation policy.
- **SDKs and adoption:** Tier 1 SDKs (TypeScript, Python, Go, C#) supported 2026-07-28 at release; Rust is in beta. Tier 1 SDKs see about half a billion downloads per month; the TS and Python SDKs each passed 1B total.
- **Leadership:** lead maintainers are David Soria Parra and Den Delimarsky. The project is "a Series of LF Projects, LLC".
- **Third-party take:** Cloudflare describes the release as "the next generation of MCP" — [Cloudflare blog (search result)](https://blog.cloudflare.com/mcp-v2/)

**Governance**
- The Linux Foundation formed the **Agentic AI Foundation (AAIF)** on **Dec 9, 2025**, anchored by Anthropic's MCP, Block's goose and OpenAI's AGENTS.md.
- MCP is a directed fund under the LF. Technical direction stays with the MCP maintainers, and the AAIF board handles strategy and membership.
- [WorkOS](https://workos.com/blog/the-linux-foundation-launches-the-aaif); [blckalpaca analysis](https://blckalpaca.at/en/knowledge-base/ai-agents/a2a-protocol-basics/linux-foundation-aaif-bedeutung)
- Envoy AI Gateway, now renamed **"Agent Router"**, is also an AAIF project (Apache 2.0) — [GitHub (fetched)](https://github.com/envoyproxy/ai-gateway)

**A2A (Agent2Agent)**
- **Origin [OLDER]:** announced by Google in April 2025 — [Google Developers blog (bg)](https://developers.googleblog.com/en/a2a-a-new-era-of-agent-interoperability/)
- **Governance:** donated to the Linux Foundation on Jun 23, 2025, with founding members AWS, Cisco, Google, Microsoft, Salesforce, SAP and ServiceNow — [blckalpaca](https://blckalpaca.at/en/knowledge-base/ai-agents/a2a-protocol-basics/linux-foundation-aaif-bedeutung)
  - Techzine reports Google is transferring A2A to the AAIF — [Techzine](https://www.techzine.eu/news/devops/143659/google-transfers-a2a-to-the-agentic-ai-foundation/)
  - The sources don't clearly reconcile whether A2A sits in the AAIF or directly under the LF.

**A2A spec releases** — [A2A GitHub releases (fetched)](https://github.com/a2aproject/A2A/releases)
- **v0.2.x (May–Jul 2025):** JSON-RPC 2.0 alignment, gRPC and REST definitions, extensions, multiple transports in the Agent Card.
- **v0.3.0 (Jul 30, 2025):** the well-known path changed from `agent.json` to `agent-card.json`. It added mTLS, per-skill security and **signed Agent Cards** (`signatures`).
- **v1.0.0 (Mar 12, 2026)** was a major breaking release:
  - added a `tasks/list` method
  - replaced OAuth implicit and password flows with device code and PKCE
  - removed the version segment from HTTP URLs
  - separated the core protocol from transport mappings
  - added gRPC multi-tenancy
- **v1.0.1 (May 28, 2026):** prefers `application/a2a+json`.
- **Bindings and Agent Card:** v1.0 has three bindings: JSON-RPC 2.0 over HTTPS, gRPC and HTTP+JSON/REST. The canonical model is Protocol Buffers, also published as JSON Schema 2020-12. Interfaces are declared in `supportedInterfaces[]` of the Agent Card at `/.well-known/agent-card.json` — [AliceLabs guide (secondary)](https://alicelabs.ai/en/insights/a2a-protocol-guide-2026); [Tyk](https://tyk.io/learning-center/a2a-protocol-architecture-and-technical-specification/)
- **Division of labor:** MCP connects agents to tools and data; A2A connects agents to agents — [blckalpaca](https://blckalpaca.at/en/knowledge-base/ai-agents/a2a-protocol-basics/linux-foundation-aaif-bedeutung)

### Inferences
- **Statelessness makes MCP cloud-native.** Deploy MCP servers as ordinary stateless HTTP services (Lambda, Cloud Run, Azure Functions, containers behind any load balancer). Use `Mcp-Method` / `Mcp-Name` headers in API gateways and WAFs for per-tool authorization and rate limits. Use `ttlMs` to cache tool lists.
- **Migration risk:** servers that relied on session IDs or server-initiated sampling must refactor to explicit handles and MRTR. Clients and servers built on 2025-era SDKs may still speak 2025-06-18 or 2025-11-25, and version negotiation covers the interop.
- **Security posture in 2026:** OAuth 2.1 + PKCE, CIMD instead of DCR, audience-bound tokens, issuer validation, and treating tool descriptions and outputs as untrusted (prompt injection and tool poisoning).

- modelcontextprotocol.io and a2a-protocol.org were DNS-unreachable, so MCP transport and auth details for 2026-07-28 come from the blog post plus background knowledge of 2025 revisions.
- I couldn't confirm whether stdio changed in 2026-07-28; the blog does not mention it.
- I couldn't confirm A2A's exact current home (AAIF vs a separate LF project) or the date of the A2A-to-AAIF transfer.

## 6. Cloud deployment of agents: async workers, sandboxed code execution, durable execution, state storage

### Takeaway
Long-running agents are deployed as **durable, resumable workflows**: Temporal, Step Functions, LangGraph or MAF checkpointing, or the managed runtimes' built-in sessions. Work fans out through queues to workers.

Agent-generated code runs in **isolated sandboxes**, with three main isolation choices:
- **Firecracker microVMs** (E2B, AWS Lambda/AgentCore): strongest
- **gVisor user-space kernels** (Modal, Cloud Run gen1): middle
- plain containers: weakest

State lives in a checkpoint store (Postgres, DynamoDB, Cosmos DB, Firestore) plus object storage for artifacts.

### Cited Findings

**Sandboxes**
- **Isolation models:** E2B uses Firecracker microVMs, purpose-built for untrusted code. Modal sandboxes use gVisor, inside a broader serverless platform with GPUs — [Northflank](https://northflank.com/blog/e2b-vs-modal); [Modal guide](https://modal.com/resources/best-code-execution-sandboxes-tool-calling-ai-agents)
- **Security tradeoff:** microVMs give a hardware virtualization boundary, separating guest kernel from host kernel, which is stronger than gVisor's syscall interception. Firecracker also powers AWS Lambda — [Noqta guide](https://noqta.tn/en/blog/ai-agent-sandbox-secure-code-execution-2026)
- **Cold starts (vendor or comparison claims):**
  - E2B under 200 ms; Modal about 300 ms–2 s depending on image — [Morph](https://www.morphllm.com/comparisons/e2b-vs-modal)
  - Firecracker snapshot-restore can provision in about 28 ms — [Noqta](https://noqta.tn/en/blog/ai-agent-sandbox-secure-code-execution-2026)
- **GPU and maturity:** E2B is CPU-only; Modal supports GPUs. Modal's V2 sandbox backend is in beta — [Northflank](https://northflank.com/blog/e2b-vs-modal)
- **Other options:** AWS AgentCore Code Interpreter (microVM), Vercel Sandbox and Cloudflare Sandbox SDK — [Morph](https://www.morphllm.com/ai-agent-sandbox)
- **[OLDER] Firecracker paper (NSDI 2020):** microVMs boot in about 125 ms with under 5 MiB memory overhead each — [Firecracker NSDI paper (bg)](https://www.usenix.org/conference/nsdi20/presentation/agache)
- **gVisor:** runs a user-space "application kernel" (the Sentry) that intercepts container syscalls — [gVisor docs (bg)](https://gvisor.dev/docs/)
- **Built-in sandboxes:** AgentCore includes Code Interpreter and Browser tools — [AgentCore samples (fetched)](https://github.com/awslabs/amazon-bedrock-agentcore-samples). The OpenAI Agents SDK has "sandbox agents" that work inside a container on long tasks — [openai-agents-python (fetched)](https://github.com/openai/openai-agents-python)

**Durable execution**
- **Temporal + OpenAI Agents SDK:**
  - Developed with OpenAI; public preview for the Python SDK (Sept 2025).
  - Agents survive rate limits, network failures and crashes.
  - `activity_as_tool` turns Temporal Activities into agent tools, configured via `OpenAIAgentsPlugin`.
  - [Temporal blog](https://temporal.io/blog/announcing-openai-agents-sdk-integration); [Temporal docs](https://docs.temporal.io/ai/cookbook/openai-agents-sdk-python); [InfoQ](https://www.infoq.com/news/2025/09/temporal-aiagent)
  - In April 2026 Temporal and OpenAI released a Temporal extension for OpenAI sandbox agents: session management, backend switching, and forking a running agent onto a different sandbox provider — [Temporal blog](https://temporal.io/blog/introducing-temporal-and-agentic-sandboxes-openai-agents-sdk)
- **Temporal model (bg):** workflows must be deterministic and are reconstructed by replaying event history. Non-deterministic work (LLM calls, tool calls) goes in Activities with automatic retries — [Temporal docs (bg)](https://docs.temporal.io/workflows)
- **AWS Step Functions (bg):**
  - **Standard workflows** run up to one year (exactly-once); **Express workflows** up to five minutes (at-least-once).
  - Optimized Bedrock integrations (e.g., InvokeModel).
  - The `.waitForTaskToken` callback pattern pauses for human approval or external jobs.
  - [Step Functions docs (bg)](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-standard-vs-express.html)
- **Framework-level durability:** LangGraph durable execution and checkpointing — [LangGraph (fetched)](https://github.com/langchain-ai/langgraph); MAF checkpointing, time-travel and "durability and restartability" — [MAF (fetched)](https://github.com/microsoft/agent-framework)
- **Production practice (Anthropic):** resume from checkpoints rather than restarting; retry logic; rainbow deployments for long-running agents — [Anthropic (fetched)](https://www.anthropic.com/engineering/multi-agent-research-system)
- **MCP-level async:** the Tasks extension (`tasks/get` polling, `tasks/update`) supports long-running tool calls — [MCP blog (fetched)](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- **Managed runtimes:** AgentCore Runtime supports up to 8-hour sessions in per-session microVMs — [AWS docs (bg)](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html). Gemini Enterprise adds long-running agents and an Inbox to monitor them — [Pasquale Pillitteri](https://pasqualepillitteri.it/en/news/1311/gemini-enterprise-agent-platform-google-next-2026)

### Inferences
- **Reference async pattern:**
  1. The API accepts a task and returns a task ID (HTTP 202).
  2. The request is enqueued (SQS / Pub/Sub / Service Bus).
  3. A durable workflow (Temporal / Step Functions / Durable Functions / LangGraph) drives the agent loop. Each LLM or tool call is a retried activity.
  4. Code runs in a per-task microVM sandbox.
  5. Checkpoints go to Postgres, DynamoDB, Cosmos DB or Firestore; artifacts go to S3, GCS or Blob.
  6. Progress streams to the client over SSE or WebSocket, or via webhooks.
  7. HITL uses task tokens or signals.
- **Choosing an isolation tier:**
  - untrusted user-supplied or agent-generated code → microVM
  - semi-trusted code that needs GPUs → gVisor (e.g., Modal)
  - containers only for trusted code

## 7. Caching: provider prompt caching, semantic caching, response caching, embedding caches

### Takeaway
Prompt (prefix/KV) caching is the single biggest cost lever for agents and RAG.

| Provider | Mechanism | Hit price | TTL |
|---|---|---|---|
| Anthropic | Explicit or automatic breakpoints; write premium | 0.1x base (0.05x Opus/Sonnet 5.5; 0.025x Fable/Mythos 5.1) | 5 min default, 1 h option |
| OpenAI | Automatic prefix caching | Up to 90% off | In-memory; 24 h extended (pre-5.6); 30 min `ttl` (GPT-5.6+, writes now billed) |
| Gemini | Implicit (free) or explicit (storage-billed) | 90% off on 2.5+ models | Configurable for explicit caches |

Semantic caching (GPTCache, Redis LangCache, gateway plugins) is a separate, lossy layer. Use it only where approximate answer reuse is acceptable.

### Cited Findings

**Anthropic prompt caching (official docs, current)** — [Claude docs (fetched)](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- **Multipliers:** 5-minute cache writes cost 1.25x base input; 1-hour writes cost 2x. Reads cost 0.1x, except 0.025x for Claude Fable 5.1 and Mythos 5.1 and 0.05x for Claude Opus 5.5 and Sonnet 5.5.
- **TTL:** the default is 5 minutes, refreshed free on each hit and measured from request start.
- **Minimum cacheable prompt:**

| Minimum | Models |
|---|---|
| 512 tokens | Fable 5.1, Mythos 5.1, Opus 5.5, Opus 5, Sonnet 5.5, Fable 5, Mythos 5, Haiku 5.5 |
| 1,024 tokens | Opus 4.8, Sonnet 5, Sonnet 4.6/4.5 |
| 2,048 tokens | Opus 4.7, Mythos Preview |
| 4,096 tokens | Opus 4.6/4.5, Haiku 4.5 |

  Shorter prompts silently don't cache.
- **Breakpoints:** up to 4 per request (automatic caching uses one). Lookback is 20 blocks, and writes happen only at breakpoints.
- **Invalidation hierarchy:** tools → system → messages. Changing tool definitions invalidates everything. Toggling web search or citations invalidates system and messages. `tool_choice` or image changes invalidate messages.
- **Automatic caching:** a top-level `cache_control` (e.g., `{"type":"ephemeral","ttl":"1h"}`) moves the breakpoint forward as the conversation grows. It isn't available on the legacy Bedrock integration for Opus 4.6 and earlier.
- **Example prices ($/MTok: base input / 5-minute write / hit / output):**

| Model | Base input | 5-min write | Hit | Output |
|---|---|---|---|---|
| Opus 5.5 | $4 | $5 | $0.20 | $20 |
| Sonnet 5.5 | $2 | $2.50 | $0.10 | $10 |
| Haiku 5.5 (≤100K-token prompts) | $0.10 | $0.125 | $0.01 | $0.50 |

**OpenAI prompt caching**
- **Retention modes:** caching is automatic. Default retention is `in_memory`. **Extended retention `prompt_cache_retention: "24h"`** keeps prefixes up to 24 h on gpt-5.5, 5.4, 5.2, 5.1, 5 and 4.1. Extended caching offloads KV tensors to GPU-local storage; only KV tensors persist, not prompt text. Pricing is the same for both modes — [OpenAI docs (search snippet)](https://developers.openai.com/api/docs/guides/prompt-caching)
- **GPT-5.6 and later:** `prompt_cache_retention` is deprecated in favor of `prompt_cache_options.ttl`, whose only value is `30m` (also the default) — [OpenAI docs (search snippet)](https://developers.openai.com/api/docs/guides/prompt-caching)
  - **Cache writes are now billed on gpt-5.6+.** Earlier models had free writes — [Microsoft Foundry docs (search snippet)](https://learn.microsoft.com/en-my/Azure/foundry/openai/how-to/prompt-caching)
- **Routing and minimum size:** `prompt_cache_key` improves routing to cached prefixes. Caching applies at 1,024+ tokens — [LiteLLM docs](https://docs.litellm.ai/docs/completion/prompt_caching.md); [third-party summary](https://leanlm.ai/blog/prompt-caching)
- **Discount levels:** about 50% on older models, about 90% on newer GPT-5.x — [third-party, conflicting sources](https://www.morphllm.com/prompt-caching)
- **[OLDER]** OpenAI's original Oct 2024 launch gave a 50% discount at ≥1,024 tokens in 128-token increments — [OpenAI (bg)](https://openai.com/index/api-prompt-caching/)

**Google Gemini context caching**
- Implicit caching is on by default with no storage cost and a 90% discount on cached tokens.
- Explicit caching bills cache-creation tokens at the normal input price plus time-based storage. Cached-input discounts are 90% on Gemini 2.5+ and 75% on Gemini 2.0 — [Google Cloud docs (search snippet)](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/context-cache/context-cache-overview)
- **[OLDER]** Implicit caching launched for Gemini 2.5 in May 2025 at a 75% discount — [Google Developers blog](https://developers.googleblog.com/en/gemini-2-5-models-now-support-implicit-caching/)
- **Conflicting figures:** third-party numbers vary (75% vs 90%; explicit storage of $1.00/MTok-hour for Flash, $4.50/MTok-hour for 3.1 Pro), and I couldn't verify them — [Future AGI](https://futureagi.com/blog/understanding-prompt-caching-for-faster-ai-responses/); [techjacksolutions](https://techjacksolutions.com/ai-tools/google-gemini/gemini-context-caching-cost-optimization/)

**Semantic caching**
- **GPTCache (Zilliz, MIT):**
  - **Components:** embedding generator; vector store (Milvus, FAISS, Chroma, PGVector, …); cache storage (SQLite, Postgres, Redis, …); similarity evaluator; and LRU/FIFO/LFU eviction.
  - **Claims:** 10x cost and 100x speed improvements (headline claims).
  - **Caveats:** false positives and negatives (monitor hit ratio and recall), count-only eviction, and in-memory caches that are per-pod.
  - **Maintenance:** no longer adds new LLM API adapters; use the generic get/set API.
  - [GitHub (fetched)](https://github.com/zilliztech/GPTCache)
- **Redis LangCache:**
  - A managed semantic caching REST service on the Redis vector database. Embeddings are handled for you, with configurable similarity thresholds, TTLs and eviction, in a cache-aside pattern.
  - Cache hits avoid output-token cost.
  - [Redis docs](https://redis.io/docs/latest/develop/ai/langcache); [Redis tutorial](https://redis.io/tutorials/semantic-caching-with-redis-langcache/)
  - Availability is described as preview, with an official private-preview signup — [tessl skill page](https://tessl.io/registry/skills/github/redis/agent-skills/redis-semantic-cache)
- **Gateway-level semantic caching:** Azure APIM has a "Semantic Caching" lab (vector-similarity caching) — [Azure-Samples/AI-Gateway (fetched)](https://github.com/Azure-Samples/AI-Gateway). Kong offers semantic cache in Enterprise — [Cloudnuro](https://www.cloudnuro.ai/blog/ai-gateway-buyers-guide-2026-kong-vs-portkey-vs-litellm-vs-truefoundry)

**Other caches**
- **MCP list results:** now cacheable with `ttlMs`. Deterministic ordering keeps prompt-cache prefixes stable — [MCP blog (fetched)](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- **Embedding caches:** LangChain's `CacheBackedEmbeddings` hashes text and stores vectors in a key-value store to avoid re-embedding unchanged chunks — [LangChain docs (bg)](https://python.langchain.com/docs/how_to/caching_embeddings/)

### Inferences
- **Cache-friendly prompt layout:** static tools → static system prompt → stable documents → conversation → volatile content last. Never put timestamps or user IDs early. Keep tool lists deterministic, which MCP's sorted lists now support.
- **Anthropic TTL choice:** the 1-hour TTL pays off when a prefix is reused at intervals between 5 and 60 minutes. It breaks even versus re-writing after roughly one extra hit, since 2x vs 1.25x + 1.25x.
- **OpenAI GPT-5.6 billing change:** writes are now billed, so "free automatic caching" assumptions in older cost models are out of date.
- **Semantic caching:** best for FAQ-style, non-personalized, low-stakes queries. Use strict thresholds, tenant- and permission-scoped keys, and TTLs. Never semantically cache responses that depend on user-specific RAG context or tool side effects.

### Gaps
- I couldn't fetch OpenAI's or Google's pricing pages. Exact current cached-input discounts per model (GPT-5.6 write price; Gemini 3.x storage rates and minimum token counts) are unverified.
- I found no independent benchmark of semantic cache hit rates and false-positive rates in production.

## 8. Gateways and reliability: LLM gateways, routing and fallbacks, rate limits, retries/backoff/jitter, circuit breakers, streaming, structured outputs

### Takeaway
Production stacks put an **AI gateway** between apps and model providers. Its jobs:
- unified OpenAI-compatible API
- credential vaulting
- per-team token quotas and budgets
- routing and fallback across providers and regions
- semantic caching
- guardrails
- token metrics
- increasingly, MCP and A2A traffic

The market split, roughly:
- **OSS / self-hosted:** LiteLLM, Envoy AI Gateway (now "Agent Router", an AAIF project)
- **Enterprise API platforms:** Kong, Azure APIM
- **Edge SaaS:** Cloudflare
- **Governance SaaS:** Portkey (reportedly acquired by Palo Alto Networks, May 2026)

Client-side reliability is still classic distributed-systems practice: retries on 429/5xx with capped exponential backoff and full jitter honoring `Retry-After`, circuit breakers per backend, SSE streaming, and schema-constrained structured outputs.

### Cited Findings

**Gateways**
- **LiteLLM:**
  - OSS SDK plus a Proxy Server (AI Gateway) giving an OpenAI-format interface to 100+ providers.
  - The router does retries, fallbacks and load balancing across deployments.
  - Virtual keys, spend tracking per project or user, and logging callbacks (Langfuse, MLflow, Lunary).
  - MCP gateway, plus A2A agent invocation (LangGraph, Vertex Agent Engine, Azure AI Foundry, Bedrock AgentCore, Pydantic AI).
  - Claims 8 ms P95 overhead at 1K RPS.
  - [GitHub (fetched)](https://github.com/BerriAI/litellm)
  - A third-party source says it degrades around 2K RPS and suits Python workloads under about 500 RPS — [Cloudnuro (third-party)](https://www.cloudnuro.ai/blog/ai-gateway-buyers-guide-2026-kong-vs-portkey-vs-litellm-vs-truefoundry). This conflicts with the vendor claim and may reflect older versions.
- **Envoy AI Gateway → "Agent Router":**
  - An AAIF project (Apache 2.0) built on Envoy and Envoy Gateway: "Agent Router controls. Envoy carries."
  - One OpenAI-compatible API over hosted models, self-hosted inference and MCP servers.
  - **Two-tier pattern:** Tier 1 handles auth, top-level routing and global rate limits. Tier 2 handles self-hosted model access, with endpoint-picker inference optimization.
  - Kubernetes-native, with 21 listed providers, including OpenAI, Azure OpenAI, Gemini, Vertex, Bedrock, Anthropic, Mistral, Cohere and Groq.
  - [GitHub (fetched)](https://github.com/envoyproxy/ai-gateway)
  - A secondary source says it reached v1.0 in June 2026 — [guptadeepak (secondary)](https://guptadeepak.com/tools/top-5-ai-gateways-2026/)
- **Kong AI Gateway:** AI plugins on the Kong gateway. Semantic routing and cache, token and cost limits, PII/semantic guardrails, MCP and LLM-as-judge are Enterprise-gated. Kong's own benchmark claims it is faster than Portkey and LiteLLM (vendor claim) — [Cloudnuro](https://www.cloudnuro.ai/blog/ai-gateway-buyers-guide-2026-kong-vs-portkey-vs-litellm-vs-truefoundry); [API7](https://api7.ai/kong-ai-gateway-vs-litellm)
- **Portkey:** a governance-focused gateway with conditional routing on request metadata. Palo Alto Networks completed its acquisition on **May 29, 2026** (single secondary source). Licensing reports conflict (MIT vs Apache 2.0) — [Cloudnuro](https://www.cloudnuro.ai/blog/ai-gateway-buyers-guide-2026-kong-vs-portkey-vs-litellm-vs-truefoundry); [Future AGI](https://futureagi.com/blog/portkey-alternatives-2026)
- **Azure API Management AI gateway:**
  - Labs and capabilities: token rate limiting, token metrics emission, semantic caching, backend-pool load balancing, model routing (by model and version), content safety, MCP (OAuth credential management, client authorization), A2A-enabled agents, and a FinOps framework (automated quota controls) — [Azure-Samples/AI-Gateway (fetched)](https://github.com/Azure-Samples/AI-Gateway)
  - Named policies include `llm-token-limit` / `azure-openai-token-limit`, `llm-emit-token-metric`, `llm-semantic-cache-lookup` / `-store`, and `llm-content-safety`. Backend pools support circuit-breaker rules — [Microsoft Learn (bg)](https://learn.microsoft.com/en-us/azure/api-management/genai-gateway-capabilities)
- **Cloudflare AI Gateway:** edge proxy with caching, rate limiting, request retries, model fallback, and analytics and logging across providers — [Cloudflare docs (bg)](https://developers.cloudflare.com/ai-gateway/)
- **Selection rule of thumb:** extend existing infrastructure. Kong shops use Kong AI Gateway, Kubernetes/Envoy shops use Envoy AI Gateway, Python-first teams use LiteLLM, and governance-driven orgs use Portkey — [Cloudnuro](https://www.cloudnuro.ai/blog/ai-gateway-buyers-guide-2026-kong-vs-portkey-vs-litellm-vs-truefoundry)
- **MCP-aware gateways:** the 2026-07-28 MCP `Mcp-Method` / `Mcp-Name` headers let gateways, rate limiters and WAFs route and meter MCP traffic without parsing bodies — [MCP blog (fetched)](https://blog.modelcontextprotocol.io/posts/2026-07-28/)

**Rate limits**
- Providers enforce RPM plus token limits: TPM for OpenAI; ITPM and OTPM for Anthropic, via a token-bucket algorithm with per-tier limits. They return HTTP 429 with a `retry-after` header.
- On Anthropic, cache-read tokens do not count toward ITPM for most current models, so caching raises effective throughput — [Anthropic rate-limit docs (bg)](https://docs.claude.com/en/api/rate-limits); [OpenAI rate-limit docs (bg)](https://platform.openai.com/docs/guides/rate-limits)

**Retries, backoff, jitter, circuit breakers**
- **[OLDER, 2015] Full jitter:** `sleep = random(0, min(cap, base·2^attempt))` minimizes contention and total work versus un-jittered exponential backoff — [AWS Architecture Blog, Brooker (bg)](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)
- **Circuit breaker:** Closed → Open (fail fast after a threshold) → Half-Open (trial requests). Use it to stop hammering a failing model endpoint and to trigger fallback — [Azure Architecture Center (bg)](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker)
- **Agent-level reliability:** resume-from-checkpoint plus retries, rather than full restarts — [Anthropic (fetched)](https://www.anthropic.com/engineering/multi-agent-research-system). Temporal-wrapped agent runs survive rate limits, network failures and crashes — [Temporal](https://temporal.io/blog/announcing-openai-agents-sdk-integration)

**Streaming**
- LLM APIs stream over Server-Sent Events. Anthropic's event types are `message_start`, `content_block_start`, `content_block_delta`, `content_block_stop`, `message_delta`, `message_stop` and `ping` — [Anthropic streaming docs (bg)](https://docs.claude.com/en/docs/build-with-claude/streaming)
- MCP Streamable HTTP can also respond with an SSE stream. Since 2025-11-25, servers may disconnect SSE streams at will, with resumption via GET and event IDs — [MCP changelog (fetched)](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-11-25/changelog.mdx)

**Structured outputs**
- **OpenAI Structured Outputs (Aug 2024):** constrained decoding with `strict: true` on JSON Schema. gpt-4o-2024-08-06 scored 100% schema adherence on OpenAI's eval, versus under 40% for gpt-4-0613 — [OpenAI (bg)](https://openai.com/index/introducing-structured-outputs-in-the-api/)
- **Anthropic structured outputs:** JSON-schema-constrained outputs and strict tool use (public beta from Nov 2025) — [Claude docs (bg)](https://docs.claude.com/en/docs/build-with-claude/structured-outputs)
- **MCP:** structured tool output (`outputSchema` / `structuredContent`) since 2025-06-18 — [MCP spec (bg)](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

### Inferences
- **Reliability layering:**
  - **Client SDK:** retries with jittered backoff on 429, 500, 503 and 529 (honor `Retry-After`; cap attempts).
  - **Gateway:** per-backend circuit breaker, then fallback to the same model in another region or account, then fallback to an equivalent model. Token-based quotas per tenant.
  - **Workflow engine:** durable retries for long tasks.
  - **App:** stream partial output over SSE, with idempotency keys for side-effecting tools.
- **Fallback quality risk:** cross-model fallbacks change behavior and can break prompt caches, since caches are model-specific. Prefer same-model, cross-region fallback first, e.g., Bedrock cross-region inference, Azure global or data-zone deployments, or Vertex global endpoints.

- Microsoft Learn, Cloudflare and OpenAI docs were unreachable, so APIM policy names, Cloudflare features and rate-limit details come from background knowledge.
- I couldn't verify Portkey's acquisition or Envoy AI Gateway v1.0 against primary press releases.

## 9. Reference architecture: a typical production GenAI stack on AWS / GCP / Azure

### Takeaway
All three clouds converge on the same logical layers:
1. edge/WAF + API layer
2. app/orchestration compute (serverless containers or managed agent runtime)
3. model access through an AI gateway (with guardrails)
4. retrieval layer (managed RAG/search + vector store)
5. state (conversation/checkpoint DB, cache)
6. async/durable workflows + queues
7. sandboxed tools exposed via MCP
8. identity (workload identity, OAuth for tools)
9. observability/evals (OpenTelemetry traces, token metrics)
10. private networking

Microsoft's "Baseline Microsoft Foundry chat" architecture is the most explicit published blueprint.

### Cited Findings

**Azure baseline (Azure Architecture Center: "Baseline Microsoft Foundry chat reference architecture")**
- **Front end:** a chat UI on zone-redundant App Service behind Application Gateway with WAF.
- **Agent:** Foundry Agent Service in the "standard" setup, using customer-owned Cosmos DB (thread/state storage), Azure AI Search (vector knowledge) and Storage (files). These dependencies are availability-critical, so they need zone redundancy.
- **Network and identity:** private endpoints everywhere; egress forced through Azure Firewall; managed identities.
- **Observability:** Azure Monitor / Application Insights.
- [Azure Architecture Center (bg)](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/architecture/baseline-microsoft-foundry-chat)
- **Gateway:** APIM fronts model endpoints for token limits, load balancing, semantic caching and MCP/A2A exposure — [Azure-Samples/AI-Gateway (fetched)](https://github.com/Azure-Samples/AI-Gateway)
- **Knowledge:** Foundry IQ knowledge bases exposed over MCP with Entra-identity ACL enforcement — [Microsoft Foundry devblog](https://devblogs.microsoft.com/foundry/foundry-iq-agent-framework-integration/)

**AWS**
- **Agent runtime:** Bedrock AgentCore.
  - Runtime (serverless agent hosting)
  - Gateway (APIs and Lambda → MCP tools)
  - Identity, Memory
  - Code Interpreter, Browser
  - Observability (OpenTelemetry), Evaluation
  - Policy (Cedar)
  - [AgentCore samples (fetched)](https://github.com/awslabs/amazon-bedrock-agentcore-samples)
- **Guardrails:** Bedrock Guardrails integrated into AgentCore since Jun 2026 — [tech-insider.org (secondary)](https://tech-insider.org/aws-bedrock-agentcore-vs-azure-ai-foundry-vs-vertex-ai-agent-builder-2026/)
- **Retrieval:** Bedrock Knowledge Bases (OpenSearch Serverless, S3 Vectors, Aurora pgvector, Neptune GraphRAG) — [AWS docs (bg)](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base.html)
- **Durable workflows:** Step Functions (Standard up to 1 year; `.waitForTaskToken` for HITL) — [AWS docs (bg)](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-standard-vs-express.html)

**Google Cloud**
- **Platform:** the Gemini Enterprise Agent Platform (successor to Vertex AI). It includes Agent Engine runtime, Agent Studio, Agent Gateway, Model Garden (200+ models), ADK, and RAG Engine / Vertex AI Search — [HPCwire](https://hpcwire.com/aiwire/2026/04/23/google-unveils-gemini-enterprise-agent-platform); [Pasquale Pillitteri](https://pasqualepillitteri.it/en/news/1311/gemini-enterprise-agent-platform-google-next-2026)
- **Deployment:** ADK agents deploy to Cloud Run or Agent Engine — [adk-python (fetched)](https://github.com/google/adk-python)

**Cross-cutting**
- **OpenTelemetry:** the common tracing substrate across MAF, AgentCore Observability and LangSmith/LangGraph tooling — [MAF (fetched)](https://github.com/microsoft/agent-framework); [AgentCore samples (fetched)](https://github.com/awslabs/amazon-bedrock-agentcore-samples)
- **Feature-maturity comparison (Sept 2026, secondary):**
  - AgentCore is GA for browser and evaluations; AWS has no first-party red-teaming service.
  - Foundry has GA red teaming (PyRIT-based) but a limited optimization loop.
  - [tech-insider.org (secondary)](https://tech-insider.org/aws-bedrock-agentcore-vs-azure-ai-foundry-vs-vertex-ai-agent-builder-2026/)

### Inferences

Typical stack, layer by layer:

| Layer | AWS | GCP | Azure |
|---|---|---|---|
| Edge / API | CloudFront + WAF + API Gateway or ALB | Cloud Load Balancing + Cloud Armor + API Gateway/Apigee | Front Door / App Gateway WAF + APIM |
| App compute | Lambda / ECS Fargate / EKS | Cloud Run / GKE | App Service / Container Apps / AKS |
| Agent runtime | Bedrock AgentCore Runtime | Agent Engine (Gemini Enterprise Agent Platform) | Foundry Agent Service (hosted agents) |
| Models | Bedrock (Claude, Nova, Llama, …) + cross-region inference | Gemini + Model Garden (incl. Claude) | Foundry Models (OpenAI, Claude, …) |
| AI gateway | LiteLLM/Kong/Envoy on EKS, or AgentCore Gateway for tools | Agent Gateway / Apigee | APIM AI gateway |
| Guardrails | Bedrock Guardrails | Model Armor / safety filters | Azure AI Content Safety |
| Retrieval | Bedrock KB + OpenSearch Serverless / S3 Vectors / Aurora pgvector | RAG Engine / Vertex AI Search / AlloyDB pgvector / Vector Search | Azure AI Search + Foundry IQ |
| State | DynamoDB, ElastiCache/MemoryDB, AgentCore Memory | Firestore, Memorystore, Agent Engine Sessions/Memory Bank | Cosmos DB, Azure Cache for Redis |
| Async / durable | SQS/EventBridge + Step Functions (or Temporal) | Pub/Sub, Cloud Tasks, Workflows (or Temporal) | Service Bus + Durable Functions (or Temporal) |
| Sandbox | AgentCore Code Interpreter (microVM) | Agent Engine code execution / Cloud Run (gVisor) | Container Apps dynamic sessions |
| Observability | CloudWatch + X-Ray / AgentCore Observability (OTel) | Cloud Trace/Logging | Azure Monitor / App Insights |

These cross-cloud mappings are my synthesis from the components cited above plus background knowledge. The GCP Model Armor, Agent Engine Sessions/Memory Bank and Azure Container Apps dynamic sessions entries are bg and were not verified this session.

- **Request flow (synchronous chat):**
  1. client
  2. WAF/API
  3. app or agent runtime
  4. (semantic cache check)
  5. retrieval (hybrid + rerank, ACL-filtered)
  6. AI gateway (quota, routing, fallback, guardrails)
  7. model (prompt-cached prefix)
  8. SSE stream back to the client
  9. traces and token metrics to OTel
- **Request flow (long task):**
  1. Return 202 with a task ID.
  2. Queue the task.
  3. A durable workflow runs the agent loop.
  4. Tools run via MCP (stateless HTTP servers behind the gateway) and in a sandbox microVM.
  5. Checkpoints are written to the DB.
  6. The client is notified via webhook or SSE.
- **2026 design defaults:**
  - MCP for every tool boundary
  - A2A for cross-team or cross-vendor agent delegation
  - OAuth 2.1 / workload identity end-to-end
  - private networking with controlled egress, which is critical for agents with web or browser tools
  - evals and red teaming in CI/CD
